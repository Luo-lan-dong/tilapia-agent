## 三、违规项（需修复）

### 3.1 六个通用组件超 200 行上限且无豁免注释（中优先级）

违反 `coding-standards.md` 4.3 节「文件长度规范」：通用组件建议上限 200 行，超限应在文件顶部注释说明原因。项目内其他超限文件（AppLayout、InstallCommandModal、PlanReviewPanel、TaskNew、useTaskBuildingChat 等）均写了豁免 / 职责说明，唯独以下 6 个未写：

| ------------------------------------ | --- | --- | --------------------------- |
| `components/TaskNewChatPanel.tsx`    | 283 | +83 | 补豁免注释或拆分（消息渲染 / 上传 / 技能步骤区） |
| `components/LLMModelsPanel.tsx`      | 271 | +71 | 补豁免注释或拆分（列表 / 表单 / 启用切换）    |
| `components/TaskDetailArtifacts.tsx` | 268 | +68 | 补豁免注释或拆分（树构建 / 操作按钮）        |
| `components/TaskNewRightPanel.tsx`   | 253 | +53 | 补豁免注释或拆分                    |
| `components/TaskNewInputBar.tsx`     | 242 | +42 | 补豁免注释或拆分（输入区 / 模式选择 / 附件）   |
| `components/TaskTable.tsx`           | 220 | +20 | 补豁免注释或拆分（列定义外提）             |

### 3.2 useNodeMetricsPolling 重复实现轮询（中优先级）

违反「统一模式 / 不造轮子」原则：其余 6 个 hook 均复用 `usePolling`，唯独 `hooks/useNodeMetricsPolling.ts`（164 行）自行实现了 AbortController + setTimeout + setInterval 全套轮询逻辑。



* 建议：`useNodeMetricsPolling` 内部组合 `usePolling` 管理 metrics 轮询，节点详情加载单独保留，消除重复实现与维护成本。

### 3.3 构建产物过大（低优先级 / 优化项）

`vite build` 输出主 chunk `index-*.js` 1.32MB（gzip 412KB），触发 Vite「chunk > 500kB」警告。



* 建议：按路由对 `pages/*` 做动态 `import()` 代码分割（React.lazy），首屏只加载 Dashboard。

仅 1 个 e2e 用例（`e2e/task-creation.spec.ts`）。`coding-standards.md` 第 9 节要求「测试覆盖核心业务流程」，当前覆盖明显不足。

## 七、主题耦合专项分析（换亮 / 暗色主题影响评估）

### 7.1 结论

**存在明显的配色过度耦合**：当前配色没有收敛到 antd token 体系，而是**三层并存**。若直接切换亮色主题，界面会严重割裂，自定义样式区域将大面积保持深色。

### 7.2 三层配色体系（耦合根源）



| 层 | 机制                                    | 规模                                                   | 是否跟随主题                                  |
| - | ------------------------------------- | ---------------------------------------------------- | --------------------------------------- |
| ① | `ConfigProvider theme` token（App.tsx） | 26 处引用 COLORS                                        | ⚠️ 跟随算法，但当前**写死** `darkAlgorithm`，无切换逻辑 |
| ② | 组件内联样式 `style={{...}}` 引用 `COLORS` 常量 | **269 处** COLORS 引用 / 33 个文件；内联 `style` 总计 **301 处** | ❌ 静态常量（`as const`），不跟随主题                |
| ③ | CSS 文件硬编码色值（`#xxx` / `rgba()`）        | **103 处** / 5 个文件                                    | ❌ 完全游离于主题体系                             |

**第③层明细**：



| CSS 文件                          | hex | rgb | 合计 |
| ------------------------------- | --- | --- | -- |
| `pages/TaskNew.css`             | 38  | 35  | 73 |
| `components/AppLayout.css`      | 16  | 5   | 21 |
| `components/WindowControls.css` | 4   | 1   | 5  |
| `App.css`                       | 2   | 0   | 2  |
| `index.css`                     | 0   | 2   | 2  |

**COLORS 引用 Top 文件**：NodeMetrics.tsx(61)、App.tsx(26)、NodeDetailInfo.tsx(16)、NodeCluster.tsx(15)、InstallCommandModal.tsx(14)、Skills.tsx(14)、Dashboard.tsx(11)、Nodes.tsx(11)。

### 7.3 换主题会出现的具体问题



1. **界面割裂**：antd 组件（Card/Table/Modal）跟随新算法变亮，而内联样式区域与 CSS 文件样式保持深色 → 深浅混杂；

2. **文字不可读**：`textSecondary: #9599A6`、`textMuted: #666B75` 在亮背景下对比度不足；

3. **状态色失效**：主色 `#32F08C`（品牌绿）在亮背景上对比度极低，告警色 `#F65A5A` 等同样失真；

4. **状态映射游离**：`STATUS_COLOR_MAP`（nodeStatus.ts）等静态色值映射不随主题变化；

5. **无切换入口**：全项目无 `theme.defaultAlgorithm` / `useToken` / `localStorage` 主题状态，需从零搭建主题状态层。

### 7.4 改造路径（若需支持亮 / 暗切换）



| 步骤 | 内容                                                                              | 影响面             |
| -- | ------------------------------------------------------------------------------- | --------------- |
| 1  | App.tsx 增加主题状态（light/dark + localStorage 持久化），算法动态切换                            | 1 文件            |
| 2  | `COLORS` 静态常量改造为基于 antd `useToken()` 的动态取值 hook（如 `useColors`），或提供亮 / 暗两套 token | 33 文件 / 269 处引用 |
| 3  | 5 个 CSS 文件 103 处硬编码色值改为 CSS 变量（`var(--color-*)`），随 `data-theme` 切换              | 5 文件            |
| 4  | `STATUS_COLOR_MAP` 等状态色映射并入主题 token                                             | 少量文件            |

**工作量评估**：涉及全部 33 个组件 / 页面文件与 5 个 CSS 文件，属中大型重构；建议在功能冻结期一次性收口，避免边改边用导致两套体系长期并存。
