# 决策文档先加载规则

## 核心原则

**修改任何功能前，必须先查找并加载该功能上一次的决策文档**，确保本次变更建立在已有决策之上，避免：
- 重复解决已解决的问题
- 破坏已有架构约束
- 与上一次的设计意图冲突

---

## 决策文档体系

OPC 中枢调度系统（tilapia-agent）项目为每次重大功能变更或架构调整维护四份文档，存放于 `docs/` 目录。**四份文档文件名统一以 ADR 三位序号 `NNN-` 开头，序号即全局主键**：按 `Glob docs/**/NNN-*`（如 `docs/**/063-*`）可一次取全某决策的 ADR/Spec/Harness/Changes：

| 文档类型 | 存放目录 | 命名格式 | 用途 |
|---------|---------|---------|------|
| ADR 架构决策记录 | `docs/adr/` | `NNN-模块名-简述.md` | 记录决策背景、备选方案、决策原因、影响分析 |
| 自然语言决策类 Spec | `docs/spec/` | `NNN-模块名-spec.md` | 描述用户故事、核心流程、降级链路、验收标准 |
| Harness 工程 Spec | `docs/spec/` | `NNN-模块名-harness.md` | 描述测试金字塔、单元/集成/契约/E2E 测试清单、CI 门禁 |
| Changes 变更清单 | `docs/spec/` | `NNN-模块名-changes.md` | **边开发边实时登记**本次决策实际修改/新增/删除的文件及函数级明细（修/增/减 + 作用说明），供后期维护快速追溯影响面 |

> **Changes 追溯范围**：变更清单适用于本规则生效后的新决策（ADR-019 起）；历史已有决策文档**不追溯**补写 Changes。
>
> **序号归属边界规则**：
> - 无自身 ADR 的 UI 迭代/附属文档（如纯前端改版 Changes）：继承**主关联 ADR** 的序号（如 `030-settings-ui-layout-changes.md`）。
> - 同一 ADR 的多份 Changes、或对既有 ADR 的修订批次：继承**基础 ADR** 序号，模块名部分区分（如 `041-context-management-p0-changes.md`）。
> - 奠基期无属主 ADR 的模块总纲 Spec（历史个案：中央调度中枢→002、任务与节点状态→003）：按工程归属推断序号，并在文档头标注「推断归属」。
> - **修订已有决策禁止新开 ADR 序号（硬约束）**：对已 Accepted 决策的修订，必须在原 ADR 内追加「修订」小节并同步更新状态/日期；仅**全新主题**才新开序号。已误开新号的修订链，须回填原文档状态为 `Superseded（被 ADR-0XX 取代）`，并在新文档与 INDEX 同步标注修订关系，确保 `Glob docs/**/NNN-*` 取到的就是当前有效决策（2026-10-07 治理：ADR-013/022 → Superseded，ADR-024/028/032/041 补修订指向，ADR-063/064 双向标注为良性范例）。

## 修改前必读流程

修改任何功能模块前，按以下顺序操作：

### 步骤 1：查找该模块的已有决策文档

推荐按 ADR 序号精确取全（序号即主键），其次按关键词模糊搜索：

- **按序号取全**：`Glob docs/**/NNN-*`（如 `docs/**/063-*` 一次拿全该决策的 ADR/Spec/Harness/Changes）；或运行 `python scripts/check_docs.py --map` 输出「ADR → 关联文档」全映射
- 按模块关键词搜索（如 `trace`、`scheduling`、`terminal`）
- 查看 `docs/INDEX.md` 索引中的 spec 和 adr 章节

### 步骤 1.5：判断是否存在已有决策文档

按以下分支处理：

#### 情况 A：找到已有决策文档
→ 继续「步骤 2」阅读

#### 情况 B：未找到任何决策文档（首次开发 / 历史遗留模块）

**必须先编写决策文档再开发**，不能直接动手写代码。

立即执行「首次开发文档化流程」（见下文），原因：

- 没有 ADR，后续维护者会重复解决已解决的问题
- 没有 Spec，业务流程无法对齐，前后端理解可能不一致
- 没有 Harness，回归测试缺少依据，bug 难以防范

**判断"是否属于首次开发"的标准**：

| 场景 | 是否需要先写决策文档 |
|------|---------------------|
| 全新模块（如新增"AI 面试评分"模块） | ✅ 必须 |
| 历史遗留模块（早期开发但没文档化） | ✅ 必须 |
| 现有模块小修小补（Bug 修复、文案调整） | ❌ 写入提交说明即可 |
| 配置类改动（端口、开关、文案） | ❌ 无需 |
| 紧急生产修复（Hotfix） | ⚠️ 修复后**必须**补充决策文档 |

## 首次开发文档化流程

> 适用于"情况 B"：未找到任何决策文档时的首次开发。

### 第一阶段：需求分析（与用户确认）

1. 与用户沟通业务目标、核心流程、边界条件
2. 列出至少 2 套备选方案（技术选型 / 架构方案）
3. 评估各方案优劣：性能、复杂度、可维护性、风险
4. 与用户确认最终方案（**获得用户确认前不要写代码**）

### 第二阶段：编写四份决策文档

按 `docs/INDEX.md` 中下一个可用 ADR 序号（查看 `1.2` 列表末尾 +1），创建：

| 文档 | 路径 | 必须包含的章节 |
|------|------|---------------|
| **ADR** | `docs/adr/NNN-模块名-简述.md` | 状态、日期、问题背景、决策、备选方案、影响、关联文档 |
| **Spec** | `docs/spec/NNN-模块名-spec.md` | 功能描述、用户故事、核心流程图、降级链路、验收标准 |
| **Harness** | `docs/spec/NNN-模块名-harness.md` | 测试金字塔、单元/集成/契约/E2E 测试清单、CI 门禁 |
| **Changes** | `docs/spec/NNN-模块名-changes.md` | 关联决策文档、变更清单表（文件 → 函数级明细）。编码前只需创建骨架，内容随开发实时登记 |

**注意**：

- 如果是小型功能（如新增一个简单接口），可适当简化，但 ADR 不可省略
- Spec 中必须画流程图（ASCII 即可），便于快速理解
- Harness 中必须列出至少 1 个 E2E 测试场景
- Changes 变更清单编码前只创建骨架，**禁止开发完成后一次性补记**

### 第三阶段：登记到 INDEX.md

按 INDEX.md 的「一、决策文档」章节格式补登记：

1. 在「1.1 自然语言决策类 Spec」追加一行（关联模块名）
2. 在「1.2 架构决策记录 ADR」追加一行（ADR 序号 + Accepted 状态）
3. 在「1.3 变更清单 Changes」追加一行（关联模块名 + Changes 文档链接）
4. 在 `docs/changelog/` 当月文件（如 `2026-10.md`）追加一条变更记录（INDEX 不内嵌更新记录，防膨胀）
5. 运行 `python scripts/check_docs.py`，确认零错误（四件套完整、INDEX 双向一致、零断链）

### 第四阶段：开发 + 边开发边校验

1. 按已编写的 Spec 流程开发
2. **每修改/新增/删除一个文件，立即同步登记到 Changes 变更清单**（文件路径、变更类型、函数/类级明细、作用说明），不得开发完成后一次性补记
3. 每完成一个核心模块，校验是否与 ADR 决策一致
4. 如果开发过程中发现需要偏离 ADR，**立即停止开发**，回到「步骤 3」更新 ADR
5. 开发完成后，按 Harness 清单补齐测试用例

### 第五阶段：完成总结

1. 在 `G:\boleyun\docs\经验.md` 追加本次开发的经验（如有踩坑）
2. 在 ADR 中追加"实际实施情况"小节（可选），记录与初版决策的偏差
3. 在 git 提交信息中引用 ADR 序号，便于追溯

## 拒绝执行的场景

以下场景，AI 应**主动拒绝**直接开发，要求先文档化：

- ❌ 用户要求"实现一个 XX 功能"且 INDEX.md 中无对应决策文档
- ❌ 用户要求"重构 XX 模块"且无既有 Spec 描述当前行为
- ❌ 用户要求"接入 XX 第三方服务"且未对比过至少 2 套方案

**标准回复模板**：

> 根据 `.trae/rules/decision-documents.md` 规则，本模块尚无决策文档。请先确认：
>
> 1. 本次开发的目标和边界
> 2. 至少 2 套备选方案及其优劣
> 3. 与您确认最终方案后，我将编写 ADR/Spec/Harness/Changes 四份决策文档
>
> 完成文档化后再开始编码。

---

### 步骤 2：阅读决策文档，理解上次决策

重点关注：
- **ADR 中的 Decision 和 Considered Options**：了解为什么选择当前方案、否决了哪些方案
- **Spec 中的核心流程和降级链路**：了解现有设计的容错策略
- **Harness 中的测试清单**：了解回归测试覆盖要求
- **Changes 变更清单**：了解上次决策实际改了哪些文件、哪些函数（修/增/减）及其作用，快速定位影响面

### 步骤 3：确认本次变更是否违反已有决策

- 如果**不违反**：按现有架构继续开发
- 如果**违反**：必须先更新 ADR 文档，说明违反的原因和新方案的合理性，获得认可后再开发

### 步骤 4：开发完成后更新决策文档

每次重大变更后，必须更新对应的 Spec / Harness / ADR 文档，并确保 Changes 变更清单已完整登记本次全部文件/函数级修改，记录本次决策，供下次开发加载。

## 文档命名规范

| 类型 | 命名格式 | 示例 |
|------|---------|------|
| ADR | `NNN-模块名-简述.md`（NNN 为三位序号） | `063-node-agent-trace-mirror.md` |
| Spec | `NNN-模块名-spec.md` | `063-node-agent-trace-mirror-spec.md` |
| Harness | `NNN-模块名-harness.md` | `063-node-agent-trace-mirror-harness.md` |
| Changes | `NNN-模块名-changes.md` | `063-node-agent-trace-mirror-changes.md` |

**序号即主键**：四份文档共享同一 `NNN`，`Glob docs/**/NNN-*` 一次取全。附属文档（调研/路线图/API 约定等）同样带号（如 `052-light-theme-color-plan.md`、`040-orchestrator-agent-loop-roadmap.md`）。

**校验工具**：`python scripts/check_docs.py` —— 四件套完整性、INDEX 双向一致性（漏登/断链）、全库 markdown 引用断链检查；`--map` 输出全映射；`--adr 63` 单查某一决策；`--tree` 输出 docs/ 全目录动态地图（AI 检索入口总览见 `docs/INDEX.md` 头部「AI 快速检索指南」）。

**存量迁移（2026-10-05）**：`docs/spec/` 存量文档已全量 `git mv` 加序号前缀；奠基期两个总纲 Spec（中央调度中枢→002、任务与节点状态→003）为推断归属。

## 违规处理

未加载历史决策文档直接修改功能，导致与已有设计冲突或重复返工的，按以下流程处理：
1. 回滚违规变更
2. 补读决策文档（从 INDEX.md 加载）
3. 基于已有决策重新设计方案
4. 总结经验，更新 `G:\boleyun\docs\经验.md`

违反「修订继承序号」硬约束（新开序号修订旧决策而未回填状态）的，按本次治理口径处理：回填原 ADR 状态为 `Superseded（被 ADR-0XX 取代）` 或补修订指向标注，INDEX 状态列同步，直至 `Glob docs/**/NNN-*` 一次取全的文档能直接反映当前有效决策（即"序号即主键"不失效）。
