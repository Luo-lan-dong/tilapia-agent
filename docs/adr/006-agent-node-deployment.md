# ADR-006：Agent 节点部署与接入方案

## 状态

Accepted

## 日期

2026-08-03

## 问题背景

OPC 项目采用分布式架构，专业 Agent 节点需要独立部署并与中央调度中枢通信。随着节点类型增多（编程、视频、文案、设计、运营、商务财税），如何快速、标准化地部署新节点成为关键问题。

核心诉求：

- 新节点接入流程简单，最好一键完成。
- 避免节点版本碎片化，便于统一升级。
- 中枢与节点边界清晰，不引入过重依赖。
- 兼顾不同操作系统和硬件环境（Windows / Linux / GPU 节点）。

## 决策

Agent 节点采用**中枢托管模板 + 安装脚本 + 自动注册**的接入方式：

1. 中枢节点为每种 Agent 类型提供安装入口，按操作系统区分（Windows / Linux）。
2. 安装包/脚本中**只包含 OPC 项目独有的 Agent 模板和程序**，不打包第三方依赖。
3. 第三方依赖（如 GPU 驱动、Python 环境、FFmpeg 等）由安装脚本内置系统命令自行安装。
4. 安装完成后，Agent 节点读取安装时注入的中枢地址和注册 Token，主动向中枢注册。
5. 后续脚本和模板迭代由中枢统一版本管理，节点通过更新脚本重新拉取。

## 备选方案

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| 方案 A（本决策）：中枢托管模板 + 脚本 + 自动注册 | 统一版本、接入简单、中枢不背第三方依赖包袱 | 需要维护多系统脚本、第三方依赖安装可能失败 | ✅ 选中 |
| 方案 B：中枢托管全量安装包 | 真正一键安装 | 包体过大、跨硬件差异难覆盖、授权复杂 | ❌ 否决 |
| 方案 C：Agent 节点完全独立部署 | 中枢无负担 | 接入繁琐、版本碎片化 | ❌ 否决 |
| 方案 D：容器化镜像分发 | 环境一致、便于扩容 | MVP 阶段引入额外复杂度、GPU 需额外配置 | ⚠️ 延后考虑 |

## 决策原因

1. **平衡统一性与灵活性**：中枢统一管控 OPC 自身模板和版本，第三方依赖由本地脚本处理。
2. **MVP 阶段可落地**：不需要搭建镜像仓库，也不需要处理大文件分发。
3. **符合节点隔离原则**：每个节点独立执行安装，环境互不干扰。
4. **保留演进空间**：后续可以平滑过渡到容器化方案（方案 D）。

## 影响

### 对系统架构的影响

- 中枢增加"Agent 模板管理"和"安装引导"两个轻量能力。
- 中枢不负责第三方依赖分发，降低带宽和存储压力。
- 节点仍保持独立部署和环境隔离。

### 对开发的影响

- 需要为每种 Agent 类型维护至少两类安装脚本（Windows / Linux）。
- 需要定义 Agent 注册 Token 生成和校验机制。
- 需要定义 Agent 版本号规范，便于后续更新。

### 对安全的影响

- 安装脚本从中枢下载，需对脚本做完整性校验（如 SHA256）。
- 注册 Token 需要设置有效期，防止被盗用。
- 建议后续引入 HTTPS 传输脚本和 Token。

### 对运维的影响

- 新节点接入流程标准化：下载脚本 → 执行安装 → 自动注册。
- 节点升级通过重新执行安装脚本完成。
- GPU 驱动等第三方依赖首次安装失败时，需要人工介入排查。
