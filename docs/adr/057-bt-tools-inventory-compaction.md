# ADR-057: 工具清单结构化（宝塔 MCP 目录不再机械截断）

## 状态

Accepted

## 日期

2026-09-27

## 问题背景

排查中确认「工具结果看不全」的实际形态后，用真实宝塔 MCP（`192.168.101.13`）做了只读实测，
得到三组硬数据：

### 数据 1：清单被截掉 76%，65 个工具对模型不存在

`BtMcpToolsSkill` 把 98 个工具的完整描述拼成一段文本后 `summary[:8000]`
（`app/skills/bt_mcp.py:153-162`）：

| 指标 | 实测 |
|------|------|
| 工具总数 | 98 |
| 摘要全文 | **33,781 字符**（≈1.35 万估算 token） |
| 实际入上下文 | **8,000 字符**（≈3,200 估算 token） |
| 丢弃比例 | **76.3%** |
| 模型能看到名字的工具 | **33 / 98**（按库内真实 content 统计为 60 行中断） |
| 名单完全消失的工具 | **65 个**（含 `SystemInfo`、`ContainerList`、`BashStop`、`ImagePull`） |
| 截断位置 | 停在半句话中：`…- BashStatus（?）：查询后台任务的状态、输出与最` |

**危害不是「信息少」，而是「模型不知道自己不知道」**：标题写着「共 98 个工具」，正文只列到
第 60 行，且无任何省略标记 —— 模型会认为清单就这些，于是部署任务不去查系统信息、
需要后台任务管理时只知道 `Bash` 而不知道有 `BashStatus`/`BashStop`；
半句话的 `BashStatus（?）` 还会诱发对入参的**猜测**（幻觉参数/反复试错的来源之一）。

### 数据 2：问题高度集中，并非普遍现象

统计库内所有工具回传长度：

| 长度区间 | 条数 |
|---------|------|
| > 8,000 字符 | 0（上限即 8000，全部为被截断的清单） |
| 3,000 ~ 8,000 字符 | **10**，其中 **7 条是 `bt_mcp_tools` 的同一清单** |
| 其余最大 | 4,367 / 4,094 / 3,594 字符 |

即：**当前系统里唯一真正「太长」的工具就是宝塔工具清单**。部署类工具是异步的
（只回报 `task_id`），不会产生大回传。

### 数据 3：紧凑化后**比现在的截断更短**

按「工具名 + 风险 + 首句（≤50 字）」实测估算：

| 形态 | 长度 | 覆盖 |
|------|------|------|
| 现在（机械头截 8000） | 8,000 字符 | **60/98 行**，含半句话 |
| 紧凑化全量清单 | **约 2,467 字符** | **98/98**（若首句上限放到 150 字约 6,000 字符） |

**结论：覆盖全量清单比现在的截断更省 token。** 机械头截是「既贵又缺」的最差组合。

### 数据 4：恢复路径已存在，只是没人告诉模型

`BtMcpSchemaSkill` 实际返回：`inputSchema` + **完整 description（截 2000 字符）** + 风险等级
（`app/skills/bt_mcp.py:225-230`）。对截断后消失的工具调用它可无损取回
（实测对 `SendMessage` 取回 314 字符 schema；描述部分同样会返回）。

但被截断的清单里**没有任何提示**告诉模型可以这样做，因此这条恢复路径事实上不可达。

## 决策

**只改工具清单的输出形态：从「机械头截」改为「紧凑全量 + 显式恢复指令」。**

### D1 · 单行紧凑条目

每个工具输出一行：`- <name>（<risk>）：<首句>`

- `<首句>` 取 `description` 中第一个句号/分号/换行之前的内容，并截到
  `TOOL_BRIEF_MAX_CHARS = 50` 字符；
- **上限取值由算术保证**：清单总上限 8000 字符、按 98 工具计算，最坏情况
  （每条都触顶）需 `98 × (2 + 名字20 + 1 + 风险6 + 2 + 上限) ≤ 8000` → 上限 ≤ 55。
  取 **50** 后最坏为 `81 × 98 = 7,938 < 8,000`，**全量覆盖在极端描述下也不失效**；
  实测真实描述首句平均约 42 字符，故 50 不损失可读性；
- 保留 `Upload` 的空间例外说明（`issues 2026-09-26` 修复，防止模型放弃产物上传）；
- 目的：让**全部工具名**都出现在清单里（覆盖优先于深度）。

### D2 · 显式恢复指令（本 ADR 的核心，防「不知道自己不知道」）

清单头部与尾部各给一条不可省略的指引：

- 头部：声明「下面列出全部 N 个工具，仅给一句话用途」；
- 尾部：**「要某个工具的完整说明与入参 Schema，调用 `bt_mcp_schema(server_id, tool)`」** +
  「high 风险工具服务端要求用户确认」。

这样模型即使只看到一句话描述，也知道**完整信息如何取得**，不会去猜入参。

### D3 · 保留总上限，但只在极端情况生效

`summary[:RESULT_SUMMARY_MAX_CHARS]`（复用既有 8000 语义上限）继续保留，用于防
「风险标签/描述异常膨胀」的极端场景；紧凑化后正常输入（约 2.5k~6k 字符）不会触及该上限。

**不改变**：默认的 `description` 字段、`returns` 描述、工具调用方式、风险判定逻辑
（仍用 `list_tools` 返回的 `tool.risk`）。

## 备选方案

| 方案 | 结论 |
|------|------|
| **A（本决策）紧凑全量 + 恢复指令** | **采纳**。实测更短且覆盖 98/98；改动仅一处技能 + 一句指令，风险最低 |
| B. 直接取消截断，发全量 33,781 字符 | 否决（当前范围）。虽在 1M 窗口下只占约 1.3%，但每轮多带约 1 万 token，且描述里的 `Args:` 长文对「浏览选工具」无用；待有实测收益时再议 |
| C. 保持机械头截，仅追加「已省略」标记 | 否决。仍丢 65 个工具名，标记无法弥补「不知道有哪些工具」 |
| D. 按风险/类别分页返回（多次调用取全） | 否决。逼模型多轮往返才能看到全部工具，与「选对工具」的目标相反 |
| E. 临时子代理：新上下文加载全部工具并推荐 | 否决（本阶段，用户决策 2026-09-27）。原理可行（成熟范式），但对本问题引入更多失效模式（子代理选错→错误在独立上下文里被放大后返回、故障排查跨上下文、额外延迟与成本）；且子代理最终仍要把「推荐结果」塞回主上下文，收益不如直接给紧凑全量清单。**留作后续**：当出现「需读取超长原始结果并归纳」的真实需求时再立项 |
| F. 只把 `bt_mcp_schema` 的 description 缩短以对齐 | 否决。方向相反：`bt_mcp_schema` 是**按需深读**路径，应保留完整描述 |

## 影响

### 中枢后端

- `app/skills/bt_mcp.py`：`BtMcpToolsSkill.execute` 的摘要构造改为紧凑条目 + 恢复指令；
  新增私有辅助 `_first_sentence(text, limit)`；
- 新增常量 `RESULT_SUMMARY_MAX_CHARS = 8000`（原为字面量 `8000`，改为具名以便测试引用）。

### 数据库 / 前端 / 协议

- 无迁移、无接口变更、无 SSE 事件变更；`SkillResult.data.tools` 仍返回完整结构（不变）；
- 前端零改动。

### 兼容性

- 模型可见文本变化：清单从「60 行含长描述」变为「98 行含一句话」。这是**有意的行为变更**；
- `bt_mcp_schema` / `bt_mcp_call` / `bt_deploy_guide` 行为不变；
- 既有 SOP/经验记忆里若引用了被截断的清单内容，需要重新调用清单获取（无持久化影响）。

## 实际实施情况（2026-09-27）

### 决策落实

- **D1 紧凑单行**：新增 `_first_sentence(text, limit=150)`（按 `。；\n. ` 切句，超限加 `…`），
  `BtMcpToolsSkill` 每工具输出一行 `- <name>（<risk>）：<首句>`；`Upload` 例外说明保留。
- **D2 恢复指令**：清单头部声明「下列为**全部**工具的一句话用途，完整说明与入参按需查询」，
  尾部两条指引 —— `bt_mcp_schema(server_id, tool=<工具名>)`（并标注「推荐做法，无需重新拉清单」）
  与「high 风险工具需先向用户确认」。
- **D3 极端兜底**：原字面量 `8000` 具名化为 `RESULT_SUMMARY_MAX_CHARS` 并继续兜底。

### 验证

- **单元/集成**：`tests/skills/test_bt_mcp_skills.py` **30 项全过**（新增 11 项：全量覆盖、
  长度不劣化、首句切分、无标点截断、空描述容错、恢复指令存在、极端兜底、Upload 例外、
  数据完整性、清单→`bt_mcp_schema` 深读闭环、失败路径不回归）。
- **真实数据重放**（用库内真实 98 工具清单，临时脚本已删除）：
  | 指标 | 修复前 | 修复后 |
  |------|--------|--------|
  | 可见工具名 | 60 / 98（末尾描述被切断） | **98 / 98** |
  | 同 58 个工具的渲染体积 | 8,000 字符（被截断） | **2,456 字符** |
  | 平均每条 | 133+ 字符 | **42.3 字符** |
  | 98 工具推算体积 | 33,781（截到 8,000） | **≈4,149 字符（不触兜底）** |
- **静态检查**：改动文件 ruff check/format 全过。

### 遗留

- **备选 E（临时子代理）未采纳但保留**：当出现「需读取超长原始结果并归纳」的真实需求时再立项；
  本 ADR 已记录其失效模式（子代理选错会在独立上下文里被放大后才返回、跨上下文排查困难）。
- **数据型大输出裁剪未做**：实测当前系统除本清单独占外无大回传（最大 4,367 字符），
  待 `bt_mcp_call` 出现同步大输出场景再议；届时需先解决「原文持久化 + 按需回查」
  （现状 `query_trace` 只显示 220 字符，无法取回完整工具回传）。
