# ADR-004：节点通信协议选型

## 状态

Accepted

## 日期

2026-08-03

## 问题背景

OPC 项目采用分布式架构：

- 中央调度中枢需要与前端控制台交互。
- 中央调度中枢需要与多个异构 Agent 节点交互。
- 节点之间禁止直接通信。
- 需要支持：节点注册、心跳、任务下发、进度上报、结果回传、异常告警。

通信协议需要在实时性、可调试性、实现复杂度之间取得平衡。

## 决策

- **前端 ↔ 中枢**：REST API + WebSocket（实时进度推送）。
- **中枢 ↔ Agent 节点**：REST API（任务下发/查询）+ WebSocket（心跳、进度上报、结果回传）。

## 备选方案

| 方案 | 优势 | 劣势 | 结论 |
|------|------|------|------|
| WebSocket + REST | 实现简单，前后端天然支持，调试方便，适合 MVP | 节点离线感知需额外心跳机制 | ✅ 选中 |
| gRPC + Protobuf | 高效、强类型、适合内部节点通信 | 前端支持需网关转换，调试复杂，增加部署依赖 | ❌ 否决 |
| MQTT | 轻量，适合大量节点订阅发布 | 需引入 Broker，增加运维复杂度 | ❌ 否决 |
| 纯 REST + 长轮询 | 最简单 | 实时性差，节点状态同步延迟高 | ❌ 否决 |

## 决策原因

1. **MVP 阶段优先简单**：WebSocket + REST 能满足所有实时通信需求，且实现成本低。
2. **前后端一致性**：前端和 Agent 节点都可以用同一套 WebSocket 事件模型与中枢通信。
3. **可调试性**：REST 和 WebSocket 都可通过浏览器开发者工具和 Postman 调试，排查问题方便。
4. **未来可扩展**：如果后期节点数量庞大或需要更严格类型约束，可局部引入 gRPC 而不影响整体架构。

## 影响

- WebSocket 消息格式统一为 `{event, payload, timestamp, request_id}`。
- 定义标准事件命名空间：`task.*`、`agent.*`、`system.*`、`hub.*`。
- Agent 节点心跳间隔 5~10 秒，中枢超时阈值 30 秒。
- 大文件不走 WebSocket，统一走共享存储路径。
