# 2026-10-05 任务秒失败排查：升级节点时漏换 tilacode（模型目录装配失败）

## 现象

用端到端探针（`tmp/e2e_probe.py`）派发一个简单任务，节点已 `assigned/running`，但：

- 任务 **4 秒内从 `running` 变 `failed`**，`progress=0`，`progress_stage/message` 均空；
- `GET /tasks/{id}/agent-trace` 返回 **0 行**（无任何节点轨迹）；
- DB `tool_call_logs`：`dispatch` → `task_accepted` → `task_failed`（间隔仅 4s）。

## 定位（按 Runbook §6.3 决策树）

1. **中枢侧**（§6.3-④）：`tasks` 行无失败原因字段；`tool_call_logs` 只看到 `task_failed`，无 reason。
2. **节点侧**（§6.3-③）：`journalctl -u opc-agent-code` 直接给出根因：

```
tilacode_session_created ... model={'providerID':'hub-deepseek-174a42f4','id':'deepseek-flash'}
GET http://127.0.0.1:4096/api/model "HTTP/1.1 200 OK"
[error] tilacode_preflight_catalog_empty  provider=hub-deepseek-174a42f4 model=deepseek-flash
[error] task_bridge_error: tilacode 模型目录为空，无法解析执行模型 hub-deepseek-174a42f4/deepseek-flash：
        节点侧 tilacode 未能装配 provider 目录（产物版本过旧或实例未就绪）。
```

即 **ADR-061 C1 派发前预检拦下**：tilacode 的模型目录（catalog）为空，无法解析工作目录里刚写入的 provider。

3. **版本比对**：
   - 节点 `bin/tilacode` = **147495040 字节，9月28**（旧）；
   - 0.6.0 包内 `bin/tilacode` = **147503232 字节，10月2**（含 catalog 装配修复）；
   - 节点 `bin/opc-agent` 已是新版，**唯独 tilacode 没换**。

## 根因

上一次节点升级是**手工命令**，只执行了
`cp <解压目录>/bin/opc-agent bin/opc-agent`，**漏掉了 `tilacode`**。
而官方 `/root/deploy-opc-agent.sh` 是 `cp -rf "${EXTRACT_DIR}/bin/." "${BIN_DIR}/"`
——会把 `opc-agent` 与 `tilacode` 一起覆盖。手工替换即绕过了这个保护。

后果：节点留着 9月28 的旧 tilacode（早于 2026-10-01 的 catalog 装配修复），
新增的 C1 预检据此立即判失败（快速失败本身是正确行为，只是暴露了二进制没更新）。

## 修复

对两台节点（先 stop 再跑官方脚本）：

```bash
systemctl stop opc-agent-code && bash /root/deploy-opc-agent.sh
# 自检：bin/opc-agent 与 bin/tilacode 大小应与解压目录一致
ls -la /opt/opc-agent-code/bin/
```

修复后复跑探针：任务正常执行（progress 0→64%，`executor_model_actual=deepseek/deepseek-flash`），
`agent-trace` 23 行（status 1 / reasoning 5 / tool 16 / text 1）——**链路与轨迹采集全部打通**。

## 经验

1. **节点升级一律用官方 `deploy-opc-agent.sh`**，不要手工 `cp` 单个二进制；它会整体覆盖 `bin/`。
2. 升级后必做自检：`ls -la /opt/opc-agent-code/bin/` 两个二进制大小是否与解压目录一致。
3. `tilacode_preflight_catalog_empty` = tilacode 太旧/未更新，不是中枢或任务的问题。
4. 任务「秒失败 + progress 0 + 轨迹 0 行」优先看节点日志的 `task_bridge_error`，而不是先怀疑中枢。
