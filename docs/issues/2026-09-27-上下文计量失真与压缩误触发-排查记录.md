> 状态：已定位根因并代码级复核；P0 修复决策见 [ADR-041 修订](../adr/041-context-management-v1.md#修订-2026-09-27p0-上下文计量与压缩触发)

> 证据等级：真实库数据 + 真实 provider usage 对照（非推断）

## 一、现象（用户实测）

1. **每发送一次对话都显示「正在压缩」**，即使这一轮实际没有产生新的压缩；
2. **上下文圆环只到 30% 多就触发压缩**，远早于设计预期的约 57%；
3. 长任务（宝塔部署类）对话经常「还没跑完就不继续调用工具」。

第 3 项已在本记录「四」中定位到独立根因（400 中断），与本记录主体的计量缺陷同源（都出在压缩投影的设计上）。

## 二、计量失真的量化证据（核心）

### 2.1 方法

用同一份真实会话（`d317b48d-d887-4788-89e0-785b10b34454`）构造生产同款请求，对 deepseek-v4-flash 发一次极小输出请求，取 provider 返回的 `usage.prompt_tokens` 与本地 `estimate_messages_tokens` 逐项对照。

### 2.2 结果

| 对照项 | 本地估算 | provider 真实 | 倍率 |
| --- | --- | --- | --- |
| 带压缩点的实际请求 | 33,168 | **20,137** | **1.65x** |
| 不压缩的原始全量历史 | 34,443 | **20,692** | **1.66x** |

派生结论：

```
context_window            = 65536
压缩触发线                 = 65536 − 8192(输出预留) − 20000(缓冲) = 37344（占窗口 57.0%）
实测 估算/真实 倍率        ≈ 1.66x
→ 触发线折算为真实 token    = 37344 / 1.66 ≈ 22434（仅占窗口 34.2%）
实测该请求真实密度          = 2.48 ~ 2.54 chars/token
代码假定常数                = CHARS_PER_TOKEN = 2（context_compaction_service.py:30-34）
```

即：**真实占用约 1/3 窗口时压缩就被触发，窗口剩余约 66% 从未被使用**；同时 `recent_keep` 的 8000（估算单位）折算真实仅约 4,800 token，尾部保留量比设计意图少约 40%。

前端圆环显示的是 `context_usage` 事件里的**真实** `prompt_tokens`，因此出现「圆环 30.7% 但后端判定 50.6% 已越线」的表面矛盾。

### 2.3 估算为何系统性偏高

`estimate_messages_tokens` 的口径是 `len(json.dumps(请求体, ensure_ascii=False)) / CHARS_PER_TOKEN`。chars/2 是按「中文正文」取的保守值，但本平台上下文里**工具回传占大头**，且多为 JSON/英文/ASCII（密度接近 3.5~4 chars/token）。混合语料的真实密度 2.5 被按 2.0 计价 → 约 1.25x；叠加 `json.dumps` 的键名/引号/转义开销全部计入字符数，共同形成 1.66x 的净高估。

## 三、压缩在越线后「每轮空转并提示」

### 3.1 触发判定读错了对象

`orchestrator.py:591` 调用 `should_pre_compact(messages, tools, model_window, prompt_messages[0]["content"])`——第一个实参是**会话原始 `messages`**，而真正发给模型的是 `project_messages()` 投影后的 `prompt_messages`。压缩只改 `context_compaction`，不改 `messages`，因此：

- 压缩完成后，下一轮的判定输入与压缩前**完全一致**；
- 估算值不会因压缩而回落 → **一旦越线就永久停在线上**。

### 3.2 提示事件在「压缩是否真的发生」之前无条件下发

`orchestrator.py:592` 的 `context_compacting` 事件位于 `compact_if_needed()` 调用**之前**且无任何条件，所以每轮都会推给前端。用户在会话 `83ca6bf0` 中连续看到的「正在压缩」正是此处。

### 3.3 库内证据（会话 `83ca6bf0-e8bc-41f6-8171-dcf82d086f73`）

| 时间 | kind | result_summary |
| --- | --- | --- |
| 01:59:45 | compaction | `{"compacted": true, "message_count": 28}` |
| 02:00:02 | compaction | `{"compacted": false, "message_count": 28}` |
| 02:02:26 | compaction | `{"compacted": false, "message_count": 28}` |
| 02:08:09 | compaction | `{"compacted": false, "message_count": 28}` |

同一会话另有 21、26 两次成功压缩（共 6 次 compaction 事件）。`_generate_summary` 的防重复判定（`context_compaction_service.py:287`）挡住了重复烧钱的摘要调用，但**挡不住「每轮都判定要压缩 + 每轮都提示用户 + 每轮都多跑一次估算」**。

## 四、同源缺陷：压缩切点切进工具轮 → provider 400 直接中断对话

### 4.1 现象与证据

会话 `83ca6bf0` 在 01:59:46 / 02:00:04 / 02:02:27 / 02:08:11 连续 4 次 LLM 调用失败，错误完全一致（`llm_usage_records` / `tool_call_logs` / `error-2026-09-26.log`）：

```
{"error":{"message":"Messages with role 'tool' must be a response to a preceding message with 'tool_calls'"}}
```

每次 400 都紧跟在一次 `compaction` 成功之后 0.7~2 秒内。`orchestrator.py:1020-1031` 捕获后直接 `error` + `done`，用户侧表现为「任务没跑完就不动了」。

### 4.2 根因（代码级）

`context_compaction_service.py:198-209` 的投影：

```python
cutoff = int(context_compaction.get("message_count") or 0)
projected = [build_checkpoint_message(...)]   # user 角色检查点
projected.extend(messages[cutoff:])            # 从 cutoff 硬切，不看角色
```

投影结果 = `user(checkpoint)` 紧跟 `tool` 消息，而 `tool` 消息的 `assistant(tool_calls)` 父级在 `cutoff` 之前被切掉 → 违反 OpenAI/DeepSeek 的 tool 协议 → 400。

复核该会话 `cutoff = 28` 的上下文：

```
ord 27 | assistant |                    ← 父级（被切掉）
ord 28 | tool      | call_00_6nADSA07tYxE   ← 投影的第一条
ord 29 | tool      | call_01_GwH3o2NDEgJA
```

### 4.3 影响面（库内全量统计）

| 会话 | 消息数 | cutoff | 切点角色 | 后果 |
| --- | --- | --- | --- | --- |
| `83ca6bf0` | 87 | 28 | **tool** | 已确认 4 次 400 中断 |
| `d317b48d` | 109 | 49 | **tool** | 同一颗雷（ord 48 assistant 被切、49 tool 成为首条） |
| `8af060e1` | 45 | 9 | **tool** | 同一颗雷 |

已启用压缩的 7 个会话中，**3 个落在工具轮边界上**（另外 4 个切点为 `assistant`）。压缩点**持久化在会话行**，一旦踩中，该会话**每次新请求都会在第一次 LLM 调用就 400**，重试与换说法均无效，只能新开会话。

### 4.4 与 ADR-041 的关系

ADR-041 只定义了「投影压缩点之后的消息」，未定义**切点必须落在工具轮边界之外**。参考实现 `借鉴/deepseek-harness-master` 明确要求「每个被压缩区间都从第一个非 system 节点开始」（`packages/compaction/compaction-basic/README.md` §Automatic triggers）。本项属 ADR-041 的设计缺口，修复须同批修订 ADR（见待办 P1）。

## 五、附带的缓存与参数观测（供 ADR-044 侧使用）

### 5.1 缓存命中率（`llm_usage_records`）

| 场景 | 调用数 | 平均命中率 | 最大 prompt | 最大 completion |
| --- | --- | --- | --- | --- |
| orchestrator | 280 | 75.8%（69 次为 0%） | 31,981 | **8,192（触顶 2 次）** |
| spec_chat | 29 | **2.1%** | 7,249 | 7,890 |
| ai_dispatch | 15 | 2.7% | 367 | 239 |
| standard_doc_gen | 1 | 0.0% | 432 | 3,439 |

### 5.2 两个附带缺陷

1. **摘要调用不可能命中缓存**：`context_compaction_service.py:295-300` 的摘要请求是「独立 system 提示 + 一团 head+tail 拼成的单条 user 消息」，不重放 system/tools/历史，无共享前缀。参考实现的做法是把「system + 上次工具声明 + 被压缩区消息」**逐字节重放**，压缩指令作为最后一条 user 追加，从而复用热前缀。
2. **`max_tokens=8192` 硬编码已触顶**：`deepseek.py:23,580`，实测 2 次 `completion_tokens == 8192`，长输出（三件套、部署收尾）存在被截断风险。

此外核对发现：`_build_payload` 仅在 `reasoning=True` 时下发 `reasoning_effort`（`deepseek.py:585-587`），而编排主链路调用 `chat_completion_stream_raw` 时未传 `reasoning`，**该参数在编排链路上从未生效**。
