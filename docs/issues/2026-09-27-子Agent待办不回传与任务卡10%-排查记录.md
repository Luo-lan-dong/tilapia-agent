# 2026-09-27 子 Agent 待办不回传与任务卡 10% 排查记录

## 现象

- 任务摘要面板「执行中」但"Agent 暂未上报待办明细"，进度恒 10%，当前动作恒"仍在执行：任务执行中"（stage=idle）
- 任务 70b82d07（登录页 + FastAPI）长时间无进展，用户手动取消；历史 completed 任务 todos 也全为 0

## 排查过程（证据链）

1. **库取证**：任务 todos=0、progress=10、stage=idle；中枢运行日志显示任务开始后**每 20 秒一次** `task_progress_updated(progress=10, stage=idle)`——全部是静默心跳（ADR-055 P2-13），无任何真实进度/待办上报
2. **心跳语义反推**：心跳仅在 `consumer.last_activity_at` 停滞超过 20s 时补发，且 message 为兜底"任务执行中"（translator.message 空）→ **tilacode session SSE 流上从未到达任何事件**（无进度看门狗 1800s 未触发，与 20s 心跳并存自洽）
3. **受控复现**：API 创建极简任务（仅创建 hello.txt）派发 code 节点，90 秒内同样零事件卡 10%
4. **产物实况**：实时打包工作目录仅 Agent 预置三件套（specs/），**无 hello.txt——tilacode 里的 AI 完全未执行**
5. **节点日志**（经宝塔 MCP Bash 通道）：Agent 日志显示订阅/排水/prompt POST 全部正常（`sse_drain_finished seq=1`），随后 `tilacode_sse_disconnected` 每 40s 循环（tilacode 端断流）；**tilacode 日志报错**：
   ```
   ERROR "Failed to drain Session" cause="SessionRunnerModel.ModelUnavailableError:
   Model unavailable: hub-deepseek-02d9a17d/deepseek-flash"
   ```
6. **配置比对**：用户级 `/root/.config/tilacode/tilacode.jsonc` 中 provider 定义**写入正确且完整**（Agent 端 upsert 正常），但 **tilacode server（10:51 启动，run=ce50d767）仅在启动时加载一次用户级配置，运行期不热重载**；任务专属 provider（命名空间含 task_id）是任务执行时才写入的 → 运行中的 server 永远看不到 → runTurn 报模型不可用

## 根因

ADR-055 D3 的 provider 动态注入设计与 tilacode server 实际行为冲突：provider 凭据只写**用户级配置**（server 启动时快照、运行期不重载），而任务命名空间（`hub-<provider>-<task_id 前 8>`）按任务动态生成，必然晚于 server 启动 → **模型永远不可用**。09-26 前任务能成功，是因为当时 tilacode server 恰在 provider 写入后重启过。

## 影响面

- 所有经中枢派发的任务在该状态下的节点上：无待办、无进度、工作目录无产物，直至 30 分钟看门狗中断或用户手动取消

## 修复（已实施，Agent 端 157 测试全过）

`workspace.upsert_provider_config` 增加 `workspace_dir` 参数：provider 定义**同时写入任务工作目录** `.tilacode/tilacode.jsonc` 的 providers 段（tilacode 项目级配置随会话**动态加载**，是生效的关键）；用户级写入保留（兼容留存）。`_resolve_session_model` 透传 workspace_dir。测试断言同步更新。

## 追加（同日晚）：节点更新后重启循环

用户 21:48 更换节点二进制（opc-agent 18MB + tilacode 147MB）后，Agent 陷入"上线→掉线"循环（周期约 50s）。Agent 日志实锤：

```
Error: Configuration is invalid at /root/.config/tilacode/tilacode.jsonc
↳ Unrecognized keys: providers, _hub_managed_providers
tilacode_already_exited returncode=1
```

**根因**：新版 tilacode 对用户级配置做严格 schema 校验，不认 ADR-055 D3 旧通道写入的顶层 `providers`/`_hub_managed_providers` 键 → server 启动即退出 → Agent 健康检查 3 次失败后退出 → systemd 再拉起 → 循环。上午配置里还没有这些键（tilacode 10:51 启动时读取的是当时干净配置），写入发生在启动之后——运行中的旧 server 不校验也不重读，所以能"带毒运行"；换新二进制重启后立即爆雷。

**处置**：
1. 节点用户级配置已备份（`tilacode.jsonc.bak-20260927`）并精简为仅 `$schema` → tilacode 可启动，循环停止
2. 探针实测（4097 试验口）：**项目配置（工作目录 `.tilacode/tilacode.jsonc`）中的 `providers` 键被新 tilacode 接受** → 修复方向成立
3. Agent 源码修订：`upsert_provider_config` **彻底移除用户级写入**（写了反而会在 server 下次重启时毒死）——provider 只写工作目录项目配置；测试更新（157 全过）
4. **遗留**：节点当前跑的 Agent 仍含旧"写用户级"逻辑，下次任务执行凭据注入会再次把毒键写回 → 复发。必须重新构建部署含本次修复的 Agent 包

## 最终根因（源码级，2026-09-27 晚定案）

**配置顶层键名复数错误**。tilacode 的 ConfigV1 schema（`packages/core/src/v1/config/config.ts:110`）顶层键是**单数 `provider`**（`provider: Record<String, ConfigProviderV1.Info>`，子结构 npm/name/options{apiKey,baseURL}/models 与 Agent 写法完全一致）；而 Agent 自 ADR-029 起一直写的是 **`providers`（复数）**——用户级配置被严格校验拒绝（"Unrecognized keys: providers"→server 启动崩），项目级配置被静默忽略 → **provider 定义从未进入模型解析清单** → runTurn 报 ModelUnavailableError → 会话零事件 → 卡 10%/无待办。

## tilacode 能力探索结论（配置热更新）

- server 暴露 `PATCH /api/config`（handlers/config.ts `update`）：`configSvc.update(payload)`（merge 写 `<目录>/config.json`）+ **`markInstanceForDisposal`**（该目录 InstanceState 标记待销毁）
- tilacode 配置在**目录 InstanceState 创建时**加载（全局配置缓存 `Duration.infinity`；模型解析为 Location 作用域）——运行中 server 不感知文件变更，必须触发实例失效
- InstanceState 按目录隔离：失效重建**只影响该目录**，不杀 server、不影响其他目录的并发任务
- `GET /api/config/providers` 可查当前生效的 provider 清单（可用于验证）

## 修复实施（Agent 端，157 测试全过）

1. `workspace.upsert_provider_config`：目录配置键名 `providers` → **`provider`**（单数）；用户级写入维持废弃
2. `tilacode_client.invalidate_config(directory)`：空 payload `PATCH /api/config`，借 markInstanceForDisposal 使目录实例失效
3. `task_bridge._prepare_session`：`_resolve_session_model` 写入 provider 后、`create_session` 前调用 invalidate_config → 重建实例时加载新 provider
4. **按任务切换模型成立**：任务 A/B 各目录各 provider + 每任务失效重建；同任务链中途换模型同样生效（新 provider upsert + 失效重建）

源码修复完成（workspace.py / tilacode_client.py / task_bridge.py + 测试），**需重新构建部署 Agent 包到节点**。部署后可用 `GET /api/config/providers?directory=<任务目录>` 验证 provider 是否进入解析清单。

## 二次定案（2026-09-27 深夜）：单数键修复部署后仍 ModelUnavailable——毒键 `_hub_managed_providers`

用户部署键名修复后重派任务 639abf4e，文件内容已正确（单数 `provider`，截图确认），但依旧 `ModelUnavailableError`，tilacode 日志 `project copy refresh projectID=global updated=[]`。

**源码级根因**：`ConfigParse.schema`（`packages/opencode/src/config/parse.ts` 的 `topLevelExtraKeys`）对配置文件**顶层任一未知键**抛 `unrecognized_keys: InvalidError` → **整个文件不参与 merge**。而 ADR-055 D3 旧代码同时写入的顶层管理键 **`_hub_managed_providers`**（`workspace.py` `_MANAGED_KEY`）不在 ConfigV1.Info schema 中——正是毒键：

- 文件里 `provider` 写得再正确，只要有这个键，整个文件被拒绝
- 节点实测证据：4 个有毒键的任务目录全部卡死（其中 639abf4e 文件里 provider 明明存在）；历史能跑的目录全部无毒键——与用户「图一能跑/图二跑不动」配置对比完全吻合（图一无管理键、图二有）

**修复（Agent 端，测试已过）**：
1. `workspace.upsert_provider_config` 不再写入 `_MANAGED_KEY`；写入时**主动剔除**该键（幂等自愈历史残留文件）
2. 节点侧 4 个毒文件已通过宝塔 MCP 现场清洗（`scripts/clean_poison_key_20260927.py`）
3. 测试补防回潮断言：`"_hub_managed_providers" not in ws_config`

**教训**：写进第三方配置文件的键必须全部来自对方 schema 白名单；自有管理元数据一律落独立文件或内存，严禁混入共享配置顶层。
