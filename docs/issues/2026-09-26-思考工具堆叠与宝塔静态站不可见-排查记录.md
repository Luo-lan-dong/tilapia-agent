## 问题一：Orchestrator 对话流「思考 - 工具」堆叠

### 现象

前端任务对话中，思考内容全部堆积在第二个「思考过程」块里（实测单块 thinking 达 **10055 字符**），而工具调用卡片一条条贴在下方，形成 "思考归思考、工具归工具" 的分离，无法看到「哪一轮思考 → 调用了哪些工具」的对应关系。

### 设计意图（用户确认）

> 一轮思考对应
> **该轮模型实际输出的工具列表**
> —— 模型输出几个工具就列出几个（支持并行多工具），
> **不是硬性限制每轮只允许调用一个工具**
> 。期望呈现：
> `思考块 N → 该轮工具卡片们 → 思考块 N+1 → ...`
> 逐回合层叠。

### 根因（代码级）

**前端「回合分割」条件只看&#x20;**`last.content`**&#x20;是否为空，而工具轮不产生正文 → 分割永不触发 → 多轮思考 / 步骤全部合并进同一条消息。**



| 文件                                          | 分支                | 现状逻辑                                      | 问题                                |
| ------------------------------------------- | ----------------- | ----------------------------------------- | --------------------------------- |
| `src\hooks\useTaskBuildingChat.ts` L261-287 | `thinking` 事件     | `last.content` 非空才新建消息，否则 `thinking` 追加合并 | 工具轮 content 为空 → 后续轮 thinking 全合并 |
| `src\hooks\useSkillSteps.ts` L35-47         | `step_started` 事件 | `last.content` 非空才新建消息，否则 steps 追加        | 工具轮 content 为空 → 后续轮步骤全挂同一消息      |

**工具轮特征**：assistant 消息 `content=''`，只携带 `thinking` + `steps`。一轮工具执行完 `last.content` 仍是空 → 下一轮的 thinking/step 继续追加 → 全部堆积。

### 证据（远程库 `task_building_sessions.messages` 实测）

会话 `13741db3-1537-4c7d-b464-c195f9a60694`（2026-09-26 09:06，宝塔建站会话）：



| 消息     | thinking 长度  | steps 数 | 说明                                             |
| ------ | ------------ | ------- | ---------------------------------------------- |
| `[12]` | 277 字符       | 0       | 截图「思考过程 1」（I'll investigate the site state...） |
| `[13]` | **10055 字符** | **9 项** | 截图「思考过程 2」——**约 4\~5 轮思考全部合并** + 9 个工具步骤全挂载    |

旁证：同会话 `[15]` 一条 assistant 消息同时携带 `bt_mcp_servers` + `bt_mcp_tools` 两个 tool\_calls——**DeepSeek 并行工具调用的直接证据**（本轮思考对应多个工具属正常行为）。

### 修复建议

**前端两处分割条件改为「content 或 steps 任一有内容即封口新建」：**



1. `useTaskBuildingChat.ts` thinking 分支：



```
// 现在：if (last.content) { 新建 }

// 改为：上一轮已有工具步骤 → 新一轮思考必须新建消息

if (last.content || (last.steps && last.steps.length > 0)) {

\&#x20; return \\\[...prev, { role: 'assistant', content: '', thinking: delta }];

}
```



1. `useSkillSteps.ts` step\_started 分支：



```
// 现在：if (last.content) { 新建 }

// 改为：上一轮步骤已结束（非 running）→ 新步骤属于新一轮，新建消息

if (last.content || (last.steps && last.steps.some((s) => s.status !== 'running'))) {

\&#x20; return \\\[...prev, { role: 'assistant', content: '', steps: \\\[step] }];

}
```

**分割语义推演（一轮内 thinking 先到、steps 后到）：**



* 新一轮 thinking 到达时：`last` 若带上一轮已完成 steps → 分割新建 ✓

* 同轮多个 tool\_calls 的 step\_started 到达时：`last.steps` 含 running 项 → 追加同消息 ✓（保持 "一轮思考 + 该轮多工具" 成组）

* 同轮后续 thinking delta：`last.content` 空且 `last.steps` 空（或属于本轮未结束）→ 追加 ✓

* 纯正文轮（无 thinking 无工具）→ 行为不变 ✓

**效果**：呈现为「思考块 N → 该轮工具卡片们 → 思考块 N+1 → ...」逐回合层叠，满足设计意图；工具数量完全由模型本轮实际输出决定，不限制并行调用。

**影响范围**：仅前端 `TaskNewChatPanel` 渲染层（消息结构不变、后端零改动、历史会话恢复渲染同样受益）。

## 问题二：宝塔 MCP 建站「能访问但面板看不到」

### 现象

通过宝塔 MCP 创建网站成功、浏览器可访问，但在宝塔面板「网站」列表看不到该站点。

### 根因

**站点创建成功，但它是「HTML 静态项目」，不属于「网站（PHP 项目）」列表 —— 宝塔面板里这是两个独立模块。**



* `HtmlProjectCreate`（HTML 分类）创建的站点：显示在面板「网站 → **静态**」Tab，`SiteList`（网站 / PHP 列表）不会列出

* 排查过程中 AI 犯了两个工具使用错误：

1. `HtmlProjectInfo` 用错参数名：传 `project_name`（服务端 schema 校验失败），正确参数是 `site_name`

2. 用 `SiteGetConfig`（**网站类**工具）查 HTML 项目配置文件 → 必然 "未找到该网站的配置文件"

### 证据（远程库 `tool_call_logs` 实测，2026-09-26 09:11-09:16）



| 时间       | 调用                                                                            | 结果                                      |
| -------- | ----------------------------------------------------------------------------- | --------------------------------------- |
| 09:11:13 | `HtmlProjectCreate` domains=`["192.168.101.13:8080"]`                         | ❌ 失败：端口范围不合法                            |
| 09:11:32 | `HtmlProjectCreate` domains=`["192.168.101.13"]` path=`/www/wwwroot/opc-test` | ✅ **创建成功**（11328ms）                     |
| 09:15:27 | `SiteList`                                                                    | ✅ 成功（网站 / PHP 列表，**不含** 192.168.101.13） |
| 09:15:59 | `HtmlProjectInfo` 传 `project_name`                                            | ❌ 参数校验失败（应传 `site_name`）                |
| 09:16:10 | `SiteGetConfig(site_name=192.168.101.13)`                                     | ❌ 未找到配置文件（工具族用错）                        |
| 09:16:30 | `HtmlProjectInfo(site_name=192.168.101.13)`                                   | ✅ 成功 ——**站点确实存在**                       |

会话 AI 最终自查结论（消息 `[13]`）：「站点是存在的，但它不属于『网站（PHP 项目）』列表，而是建成了『HTML（静态）项目』—— 宝塔里这是两个独立模块」。

### 修复建议



1. **面板侧（用户操作）**：宝塔面板「网站」页切换到「**静态**」Tab 即可看到该站点（站点名 `192.168.101.13`，根目录 `/www/wwwroot/opc-test`）。

2. **工具族规范（改&#x20;**`bt_deploy_prompts.py`**&#x20;/bt\_mcp 技能描述）**：明确区分两类工具，避免模型串用：

* 网站 / PHP 类：`SiteList` / `SiteCreate` / `SiteGetConfig` / `SiteModify` …

* HTML 静态类：`HtmlProjectInfo` / `HtmlProjectCreate` / `HtmlProjectModify` / `HtmlProjectDelete`（**查静态项目只能用这族**）

1. **参数名规范**：`HtmlProjectInfo` 入参为 `site_name`（不是 `project_name`）；模型调用前应 `bt_mcp_schema` 查参并**严格遵循 schema**（本次已查 schema 仍传错，需在提示词中强调 "参数必须与 schema 一致"）。

2. **宝塔侧异常（建议反馈官方）**：`HtmlProjectCreate` 传 `domains=["192.168.101.13:8080"]` 报 "端口范围不合法"—— 官方文档声称支持 `域名:端口` 写法（非 80 端口成为监听端口），疑似 IP 直写域名 + 端口解析 bug。临时规避：先用 80 端口创建，再 `HtmlProjectModify` 加端口。

## 后续方案：经验记忆系统（MVP 设计）

> 由问题二引发的设计讨论（2026-09-26）。目标：遇到问题 → 自动记录 → 解决后总结 → 下次同类场景命中复用，避免重复踩坑。已确认现有底座：
>
> `tool_call_logs`
>
> （原始调用）、
>
> `history_recall`
>
> （会话历史回查）、
>
> `query_trace`
>
> （执行链路）、ADR/Spec（决策沉淀）；
>
> **缺的是「结论层」**
>
> —— 把踩坑结论提炼为可跨会话复用的经验条目。

### 设计目标与定位



| 层级  | 现有能力                                    | 记忆系统补什么                     |
| --- | --------------------------------------- | --------------------------- |
| 原始层 | `tool_call_logs` + `query_trace`（发生了什么） | ——                          |
| 对话层 | `history_recall`（当次会话回查）                | 跨会话记忆                       |
| 结论层 | ADR/Spec（重大决策）                          | **轻量踩坑经验**（参数名、工具族、行为差异等小坑） |

### MVP 闭环（4 环节）



1. **① 自动记录**：`bt_mcp_call` 失败时（status=error/tool\_error）自动写入 "问题条目"—— 工具名 + 错误签名 + 参数摘要。全自动、零干预。

2. **② 会话收尾总结**：Orchestrator 收尾时检查本次会话失败条目；若后续已解决 / 给出结论 → AI 提炼「根因 + 解法」回填，**发确认信息给用户**（半自动，防止记错结论）。

3. **③ 存入经验表**：`experience_records` 表，签名可检索、跨会话复用。

4. **④ 命中注入**：`bt_mcp_call` 失败后的下一步，按 `error_signature` 查历史经验，命中则把「同类问题历史经验」注入结果摘要 —— 模型直接知道 "静态项目要用 HtmlProjectInfo、参数是 site\_name"。

### 数据表设计（草案）



```
CREATE TABLE experience\_records (

&#x20;   id              UUID PRIMARY KEY,

&#x20;   tool            VARCHAR(64)  NOT NULL,          -- 工具名（如 HtmlProjectInfo）

&#x20;   error\_signature VARCHAR(255) NOT NULL,          -- 错误签名（如 "未找到该网站的配置文件"）

&#x20;   problem         TEXT,                           -- 现象（自动快照）

&#x20;   root\_cause      TEXT,                           -- 根因（收尾总结回填）

&#x20;   solution        TEXT,                           -- 解法（收尾总结回填）

&#x20;   status          VARCHAR(16) DEFAULT 'pending',  -- pending（待总结）/ resolved（已总结）

&#x20;   session\_id      VARCHAR(64),

&#x20;   hit\_count       INTEGER DEFAULT 0,              -- 命中次数（衡量经验价值）

&#x20;   created\_at      TIMESTAMPTZ DEFAULT now(),

&#x20;   resolved\_at     TIMESTAMPTZ

);
```

### 落地点（挂现有代码，不动核心架构）



| 钩子       | 位置                                                   | 改动                                                |
| -------- | ---------------------------------------------------- | ------------------------------------------------- |
| 写入① 失败快照 | `app\skills\bt_mcp.py` `BtMcpCallSkill.execute` 失败分支 | +1 次 `experience_service.record_failure(...)`     |
| 写入② 收尾总结 | `app\agents\orchestrator.py` 收尾分支                    | 检查会话失败条目 → 提炼回填（半自动）                              |
| 检索 命中注入  | `app\skills\bt_mcp.py` 失败后 / 结果摘要                    | +1 次 `experience_service.find_matches(signature)` |
| 管理 API   | `app\api\v1\endpoints\` 新增                           | GET 列表 / 搜索、PATCH 编辑、DELETE、命中计数                  |
| 技能（可选）   | `app\skills\experience_recall.py`                    | 模型对话中主动查经验（复用 query\_trace 框架）                    |

### 前端：中枢面板「记忆」侧边栏（左侧导航）

- **位置**：左侧主侧边栏**新增导航项**（与 总览 / 节点管理 / 新建对话 / 技能 / 文档 / 日志 / 任务队列 平级，属于全局能力入口），进入独立页面 `/memory`。
- **落点（改 4 处，均为增量）**：
  1. `src\components\AppLayout.tsx` `menuItems` 新增：`{ key: 'memory', label: <Link to="/memory">记忆</Link> }`（建议放在「日志」旁边，同属链路 / 历史类）
  2. `src\App.tsx` 路由新增：`<Route path="memory" element={<Memory />} />`
  3. 新增页面 `src\pages\Memory.tsx`（列表 / 搜索 / 详情 / 编辑 / 删除 / 状态标记）
  4. `AppLayout.tsx` 的 `getSelectedKey` / `getPageTitle` 补 `memory` 分支（高亮与标题）
- **界面**：
  - 列表视图：按工具 / 错误签名 / 时间排序，显示 status（待总结 / 已解决）+ hit_count + 创建时间；支持关键词搜索
  - 详情视图：problem / root_cause / solution 三栏；可编辑（纠正 AI 记错的解法）、删除
  - 状态标记：待总结条目高亮，引导用户确认收尾总结
- **职责**：记忆归中枢统一管理（符合 "中枢只编排" 哲学）；节点只读写执行轨迹，不直接改经验。
- **对比**：与右侧工具面板 Tab（产物 / 文档 / 摘要）定位不同——右侧是"任务态"工具，随任务上下文切换；左侧记忆是"全局态"知识库，跨任务 / 跨会话常驻入口。

### 复杂度控制原则



1. **先跑通一条闭环**：只做宝塔 MCP（问题二痛点）→ 验证「失败→记录→收尾总结→命中注入」→ 再推广到所有技能（表结构天然通用）。

2. **记录全自动、总结半自动**：全自动 AI 总结易记错结论，反噬记忆质量；收尾时 AI 提议 + 用户确认。

3. **不动核心架构**：全部挂在现有 `bt_mcp_call` 技能与 `tool_call_log_service` 上，1 张表 + 2 个写入钩子 + 1 个检索钩子 + 1 个面板 Tab。

### 待决策点

- ~~总结时机：会话收尾自动 vs 用户手动触发 "记住这个坑" 命令~~ → **已定（2026-09-26）：双通道**。① 会话收尾时自动提议总结（AI 先写草案，用户确认）；② 用户随时可用自然语言触发（如"把刚才这个坑总结一下"），无需专门命令词，由对话理解即可。

* 经验范围：仅宝塔 MCP → 后续推广哪些技能（按 hit\_count 决定是否推广）

* 与 `history_recall` / `query_trace` 是否合并入口（初步建议：保留独立，互补）
